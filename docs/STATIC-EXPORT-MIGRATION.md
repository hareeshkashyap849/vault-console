# The console moved from server components to a static export

**Date:** 2026-09-17 · **Commit:** `248cd46` (export), `3344e0b` (publishing) ·
**Live:** <https://hareeshkashyap849.github.io/vault-console/>

This file exists because the change invalidated statements in eight documents, and the
workspace's rule for stale content is to record **which line is stale, what the correct
content is, and where the primary source is** -- not to delete the claim and hope nobody
noticed. Nothing here is a correction of a mistake made in those documents: each was true of
the code as it stood. The code moved.

## What changed

The console was server components. The deployment record was read from disk on every
request, the index service was reached through a Next rewrite, the chain was read in Node,
and the chain's identity crossed to the browser as `NEXT_PUBLIC_*` inlined at build time.
All four need a server at request time, and a static host runs none.

| | before | now |
|---|---|---|
| addresses | `loadDeployment()` reads the record per request | `public/api/config`, generated by `../scripts/build-runtime-config.mjs` from the same record, read once by the client (`../src/lib/runtimeConfig.ts`) |
| chain reads | server, absolute `VAULT_RPC`, `dynamic = 'force-dynamic'` | browser, the endpoint from the config, four React Query reads with `staleTime: 0` |
| index service | `/api/*` rewrite, same-origin | the config's `indexApiUrl`; NULL on a static host, which is a distinct failure kind (`no-route`) that makes no request |
| not caching | `force-dynamic` + `cache: 'no-store'` | `staleTime: 0` + `refetchOnWindowFocus` + `no-store` (unit-tested) |

`src/lib/deployment.ts` was deleted: nothing imported it, and a module that reads the record
per request contradicts the architecture. Its reasoning lives on in
`src/lib/runtimeConfig.ts` and `web3-development-execute/projects/vault-console/scripts/build-runtime-config.mjs`.

## What is still proven, what is not, and what is new

**Still proven, unchanged:** the two-sources failure independence (four independent queries,
not one shared fate); the amount-formatting discipline; the chain-vs-index reconciliation;
the real-deployment bug (`0x` is not zero); the deployment record as the single source of
addresses; contract-level evidence is untouched by any of this.

**Retired, because the mechanism it measured no longer exists:** scenario 11's before/after
pair (`Indexed to block` 12639 → 12648, `Lag` 97 → 2293) proved that
`dynamic = 'force-dynamic'` re-read on every request. There is no `force-dynamic` any more.
The property it stood for -- *nothing between the reader and the service is cached* -- is now
carried by `staleTime: 0`, `refetchOnWindowFocus`, and a unit test that asserts `no-store` is
sent. **That is not the same evidence.** The old proof was a measurement against the running
system; the new one is a unit test plus a structural argument (no server, no cache layer, and
JSON-RPC POSTs are not cacheable). It should be re-measured against the published site --
two loads, capturing the RPC requests each one issues -- and until that is done, the
replacement row belongs in `EVIDENCE-MAP.md` marked **unproven**, not absent.

**New, and measured:** the export builds five routes as static content; the published site,
opened in a real browser, reads `0x7941438ee07bea4469ccd4bec583e9fb24037f35`, chain
Base Sepolia (84532), **20 USDC** and **20 shares** live from `https://sepolia.base.org`; and
the history panel reports that the page has no route to the index service rather than blaming
a service it never asked. Evidence: `verification/out/pages-live-console-values.png`.

## Also not done

- The 51 browser assertions (`tools/browser-assert.mjs`) have not been re-run against the
  export. They were written against the server-rendered pages; several will need updating for
  the client-rendered ones, and one of them is worth keeping precisely because it asserts the
  thing this migration risked.
- `/history` on the published site has no data: a static host has no route to the index
  service. Publishing a snapshot of the index output, and pointing the config at it, is the
  next step and is the natural completion of the index-scale gap.
- The export's first paint is the loading screen (the addresses are read at runtime), so a
  reader without JavaScript sees "Loading the deployment record…" and nothing else.
